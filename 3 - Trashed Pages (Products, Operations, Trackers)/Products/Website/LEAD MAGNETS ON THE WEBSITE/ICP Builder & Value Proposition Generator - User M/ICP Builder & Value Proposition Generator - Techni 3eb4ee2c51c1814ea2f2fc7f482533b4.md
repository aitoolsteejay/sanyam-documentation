# ICP Builder & Value Proposition Generator - Technical Documentation

### **Route/page files**

- `app/tools/icp-builder/page.tsx` — server component, sets metadata (title "ICP Builder & Value Proposition Generator", canonical `https://www.myntmore.com/tools/icp-builder`), wraps `ICPBuilderClient` in `InnerLayout`.
- `app/tools/icp-builder/ICPBuilderClient.tsx` — the client-side orchestrator; owns all wizard state (`started`, `leadData`, `screen`, `intake`, `icps`, `icpResults`, `valuePropResults`) and renders `LandingPage` → `LeadGate` → the 3-screen wizard (`IntakeScreen` / `IcpBuilderScreen` / `ValuePropScreen`) inside `ScreenTransition`.

### **API endpoint**

`app/api/gemini/route.ts`, `POST /api/gemini`. This is a **generic, shared Gemini proxy** — it is not tool-specific.

- Request body: `{ prompt: string; systemPrompt?: string }` (both plain strings). If `systemPrompt` is omitted the route falls back to its own default: `"You are a B2B growth strategy expert. Return valid JSON when asked."` The route concatenates `${systemPrompt || DEFAULT_SYSTEM_PROMPT}\n\n${prompt}` into a single Gemini `contents[0].parts[0].text` message (it has no separate system-role slot; everything is one user turn).
- Response shape on success: `{ result: string }` (the raw text from Gemini, i.e. the tool must parse it itself); on failure: `{ error: string }` with `400` (missing prompt), `500` (missing API key or unexpected error), or `429` (passthrough of Gemini's own rate limit).
- **This tool never sends a `systemPrompt`** — every call from `lib/prompts.ts` passes only `prompt` (see `callGemini(prompt)` call sites in `IntakeScreen.tsx`, `IcpCard.tsx`, `IcpBuilderScreen.tsx`, `ValuePropScreen.tsx` — none pass a second argument), so the route's `DEFAULT_SYSTEM_PROMPT` is what actually gets prepended for every ICP Builder request.
- Confirmed this is the only tool in the codebase calling `/api/gemini`: every other free tool (`battle-card-generator`, `case-study-generator`, `founder-presence`, `dm-angles` (+ its `regenerate` sub-route), `lead-magnet-ideas`, `profile-optimizer`, `posting-rhythm`) has its own dedicated route under `app/api/tools/<tool>/route.ts` instead. The likely reason this tool alone uses the generic proxy is that it needs several distinct prompt shapes (offer polish, D2C description polish, ICP generation, value-prop generation) built entirely client-side in `lib/prompts.ts`, so a single passthrough endpoint avoids needing four near-identical dedicated routes.

### **AI model & prompting**

Model string, from `app/api/gemini/route.ts`: `gemini-2.5-flash` (endpoint `https://generativelanguage.googleapis.com/v1beta/models/gemini-2.5-flash:generateContent`). `generationConfig` is `{ temperature: 0.7, maxOutputTokens: 16384 }`. There is no Gemini structured-output/JSON-mode schema configured — output-format enforcement is entirely prompt-based: every prompt in `lib/prompts.ts` ends with an explicit instruction such as `"Return ONLY a valid JSON array of exactly 3 strings (no markdown, no code blocks)."` or `"Return ONLY a valid JSON array of ${n} objects..."`, and the client then extracts/parses it with `parseJsonArray` (regex `/\[[\s\S]*\]/` + `JSON.parse`).

The tool builds a **multi-stage, client-side prompt pipeline** in `components/tools/icp-builder/lib/prompts.ts`, all sharing four reusable "mandatory rule" blocks that get concatenated into each prompt:

- `NO_JARGON_RULE` — e.g. *"Keep sentences short. One idea per sentence... Say 'get more customers' not 'drive customer acquisition'..."*
- `PERSONALISATION_RULE` — *"Reference their actual company name if known. Reference their actual industry and target geography... Never write output that could apply to any generic business."*
- `GEO_AWARENESS_RULE` — *"India = relationship-driven, price-sensitive, WhatsApp and LinkedIn strong... USA = ROI-driven, direct messaging, faster decision cycles..."*
- `BUSINESS_TYPE_RULE` — adapts tone based on "Selling To" (D2C/B2B/Both) and "Business Type" (Product/Service/Hybrid).

Four prompt builders, called in this order across the wizard:

1. `buildOfferPolishPrompt(rawDescription)` (Intake screen, debounced 900ms) — rewrites the user's raw offer description into 3 distinct 2–3 sentence versions; returns a JSON array of exactly 3 strings.
2. `buildD2cPolishPrompt(rawDescription, offer, sellingTo, businessType)` (per D2C ICP card, debounced 900ms) — same idea but for a D2C customer description, grounded in the business's offer.
3. `buildIcpPrompt(offer, sellingTo, businessType, icps)` (ICP Builder screen, "Generate ICP Profiles") — the core prompt: *"You are an expert Growth Strategist skilled at building both B2B and D2C customer profiles. Generate ${n} deep, strategic Ideal Customer Profiles."* It embeds an "AUDIENCE TYPE ADAPTATION PER ICP" block requiring B2B ICPs to get professional `whoTheyAre`/`coreResponsibilities` and B2B-relevant `channelPartners` (agencies, consultants, tool vendors), while D2C ICPs get lifestyle-based fields and consumer-relevant partners (influencers, complementary brands). Requires 13 output fields per ICP including `channelPartners` (array of `{partnerType, whyTheyFit, approachAngle}`), and ends: *"Return ONLY a valid JSON array of exactly ${n} objects..."*
4. `buildValuePropPrompt(offer, sellingTo, businessType, icps)` (Value Prop screen, "Generate Value Proposition") — takes the *generated* ICPs (not the raw inputs) plus their `channelPartners`, and if any channel partners exist, adds a 4th "audience" entry for Channel Partners with its own distinct field set (`whatsInItForThem`, `idealPartnerProfile`, `partnershipSteps`, `whyPartnerWithUs`, `howToApproachThem`, using a different positioning template: *"We help [partner type] give their clients [outcome] by [what we do], while they [what they get out of it]"*). For normal ICPs it requires fields like `corePromise`, `beforeState`/`afterState`, `threeStepSystem`, `whyOthersFail`/`whyYouWin`, `contentStrategy`, `shortPitch`, `cta`, `positioning` (format *"We help [specific customer descriptor] to [their specific desired outcome] by [your specific method]"*), and `coreAngle` (must be one of `"Authority"`, `"ROI"`, `"Speed"`, or `"Trust"`).

All AI JSON responses are additionally run through `sanitize()` (`lib/sanitize.ts`), which recursively strips em-dashes (→ comma), asterisks, and hash signs from every string in the parsed structure — a belated backstop for the prompts' own *"Do NOT use em-dashes, asterisks, or hash signs"* rule.

**Retry/dedup logic in `lib/gemini.ts`** (unique among the 6 tools):

- `RETRY_DELAYS_MS = [1000, 2000, 4000]` — `callGeminiUncached` tries the real fetch up to 3 times, sleeping 1s then 2s between attempts 1→2 and 2→3 (no sleep after the final attempt). If all 3 attempts fail, there's one last fallback attempt: if the prompt is longer than `TRUNCATE_LENGTH` (2000 chars), it's truncated to 2000 chars with a `"[Truncated for reliability]"` suffix appended, on the theory that failures might be caused by prompt size (timeouts/token limits) rather than a transient error; this fallback call is not itself retried.
- `inFlight` is a `Map<string, Promise<string>>` keyed by  `${prompt} ${systemPrompt || ""}` . `callGemini()` checks this map first and returns the existing in-flight promise if the exact same prompt+systemPrompt is already being requested, instead of firing a duplicate network call; the entry is deleted via `.finally()` once the promise settles. This solves the classic React double-invoke / rapid re-render problem (e.g. a debounced effect firing twice, or a user re-triggering the same generation before the first call resolves) that would otherwise burn duplicate Gemini quota and risk racing state updates.
- `withTimeout(promise, ms)` races a promise against a `setTimeout` that rejects with `Error("timeout")`; used by `IcpBuilderScreen` and `ValuePropScreen` with `GENERATION_TIMEOUT_MS = 60000` (60s) around the whole `callGemini(...)` call (retries and all).
- `describeGeminiError(e)` maps thrown errors to user-facing copy: `"timeout"` → *"This is taking too long. Please try again."*; message containing `"GEMINI_API_KEY"` → tells the user to check Vercel config; a `"AI call failed: 429..."` match → *"Rate limited. Please try again in a moment."*; any other `AI call failed: <status>` → generic "could not reach the AI service"; anything else → generic *"Something went wrong. Please try again."*

### **Error handling / retries / rate limiting**

- Server (`app/api/gemini/route.ts`): returns `400` if `prompt` missing, `500` if `GEMINI_API_KEY` env var is unset, passes through Gemini's `429` as its own `429` with a friendly message, logs (`console.error`/`console.warn`) upstream errors and `MAX_TOKENS` truncation warnings, and wraps everything in a try/catch returning `500` with the error message on unexpected failures.
- Client (`lib/gemini.ts`): the 3-attempt retry ladder + truncated-prompt fallback described above; `parseJsonArray` throws `"no array found"` if the model didn't return anything array-shaped, which the calling screens catch and surface as *"The AI response could not be read. Please try again."* (`AI_PARSE_ERROR_MESSAGE` constant, though the inline string is what's actually shown in `IcpBuilderScreen`/`ValuePropScreen`).
- UI-level validation happens before any AI call: `IcpBuilderScreen.validate()` checks a core offer exists and, per ICP, that a type is chosen (when "Both"), and that B2B ICPs have roles/sizes/industries or D2C ICPs have a selected description, showing an inline red error message and skipping the API call if invalid.
- `IntakeScreen` and `IcpCard`'s auto-polish effects degrade gracefully on failure: if `callGemini` throws, they fall back to using the user's raw typed text (sanitized) as all 3 "options" rather than blocking the user.

### **Lead gate / lead capture**

Yes — this tool uses the shared `components/tools/shared/LeadGate.tsx` with `source="icp_builder"`, heading "Tell Us About You," gating everything after the landing page. On submit, `LeadGate` does two things in parallel: (1) submits the real HTML form via a hidden iframe (`target={ZOHO_IFRAME_NAME}`) to a dedicated Zoho form endpoint for this tool (`ZOHO_FORM_ACTIONS.icp_builder`, a `forms.zohopublic.com/flintstop/form/ICPbuilder/...` URL, using standard Zoho field names `SingleLine`/`SingleLine1`/`SingleLine2`/etc.), landing the lead in Zoho CRM; (2) inserts a row into the Supabase `leads` table (`source`, `name`, `email`, `phone`, `company_name`, `linkedin_url`, `metadata: { designation }`) as a secondary record, returning the inserted row's `id`. `ICPBuilderClient.saveProgress()` then uses that same `leadData.id` to `update` the Supabase `leads` row's `inputs` (`{ intake, icps }`) and `outputs` (`{ icpResults, valuePropResults }`) columns every time ICP results or Value Prop results change — so a lead who drops off after Step 2 (ICPs) but before Step 3 (Value Prop) is still captured with whatever they generated. Required fields: First Name, Last Name, Designation; Company/Phone/LinkedIn/Email are optional (validated via a shared `zod` schema in `LeadGate.tsx`).

### **Dependencies**

`framer-motion` (`ScreenTransition`'s fade/slide transitions via `AnimatePresence`/`motion`), `zod` (lead form validation in `LeadGate`), `lucide-react` (icons throughout), `@/lib/supabase` (Supabase client for the `leads` table, used both by `LeadGate` and `ICPBuilderClient`), Google's Gemini Generative Language API (`gemini-2.5-flash`) via server-side `fetch` in `app/api/gemini/route.ts`, and Zoho Forms (external, iframe-embedded form POST) for CRM lead capture. No dedicated npm SDK for Gemini is used — it's a raw REST `fetch` call.
